# 검색·기준 확인의 상태별 동작

화면이 요청 결과를 어떻게 나누고 각 상태에서 무엇을 보내는지 한 곳에 정리한다. 정본은 `contract/public-api-v1.openapi.yaml`(공개 계약 1.5.0)이고, 구현은 `src/lib/api.ts`(HTTP 상태·본문 검증), `src/lib/useSearchRun.ts`·`src/lib/searchStream.ts`(최초 검색), `src/lib/useConfirmSubmit.ts`(확인 답변 제출)다.

## 먼저 구분할 두 가지

| 동작             | Idempotency-Key | 본문                           | 누르는 주체 |
| ---------------- | --------------- | ------------------------------ | ----------- |
| 같은 요청 확인   | 처음과 같은 키  | 처음 요청과 같은 본문          | 사용자만    |
| 새 검색으로 시작 | 새 키           | 새 요청(원 질문부터 다시 시작) | 사용자만    |

- "같은 요청 확인"은 서버가 이미 처리했는지 모를 때 같은 요청을 한 번 더 보내 결과를 받는 일이다. 확인 제출이면 세션·버전·동작·답도 처음과 같고, 답을 바꿀 수 없다. 성공을 보장하지 않는다.
- "새 검색으로 시작"은 이전 요청과 무관한 새 검색이다. 이전 요청의 결과를 되살리지 않는다.
- 사용자가 누르는 이 두 동작과 별개로, **최초 검색의 전송 처리**가 있다. 같은 실행 키로 처리하며 사용자의 확인이 아니다.
  - SSE가 `done`·`error` 없이 끊기면 1초 뒤 한 번만 다시 받는다.
  - SSE를 열기 전에 쓸 수 없다고 판명되면(`text/event-stream`이 아님, 열기 전 연결 실패, 404·5xx) JSON 검색으로 한 번 대신한다. 422·429·504는 대신하지 않는다.
- 확인 대기와 확인 제출에는 자동 재전송이 없다. 상태 확인 버튼을 사용자가 누를 때만 다시 보낸다.

## 상태 표

HTTP 상태와 본문 검증 단계로 가른다. 504는 본문이 오류 결과처럼 생겨도 확정 결과로 보지 않는다.

| 입력·실패 위치                                     | 분류                      | 화면                               | 다음에 보낼 수 있는 것                                                       |
| -------------------------------------------------- | ------------------------- | ---------------------------------- | ---------------------------------------------------------------------------- |
| 연결 오류, 504                                     | 처리 결과 불명            | "처리 결과를 확인하지 못했습니다"  | 사용자가 누르는 "같은 요청으로 확인"만                                       |
| 504가 아닌 5xx, 본문이 유효한 오류 결과가 아님     | 처리 결과 불명            | 위와 같음                          | 위와 같음. 501처럼 명시적 종료 사유는 아래 행으로 따로 처리                  |
| 504가 아닌 5xx, 계약 검증을 통과한 `outcome=error` | 확정된 오류 결과          | 오류 결과 화면                     | "새 검색으로 시작"(새 키)만                                                  |
| 최초 검색의 2xx 본문 검증 실패                     | 응답 형식 오류            | "응답 형식이 올바르지 않습니다"    | "다시 시도"(새 검색, 새 키)                                                  |
| 확인 제출의 2xx 본문 검증 실패                     | 응답 형식 오류, 종료      | "답변을 처리하지 못했습니다"       | 같은 요청 재전송 없음. 새 검색(새 키)만                                      |
| 확인 제출 응답의 원 질문이 다름                    | 확인 응답 검증 실패, 종료 | 위와 같음                          | 같은 요청 재전송 없음. 새 검색(새 키)만                                      |
| 확인 제출의 그 밖의 4xx                            | 거절된 요청, 종료         | 위와 같음                          | 같은 요청 재전송 없음. 새 검색(새 키)만                                      |
| 409 `turn_in_progress`(최초 검색·확인 제출 공통)   | 처리 중                   | "기존 요청을 처리하고 있습니다"    | 대기 후 사용자가 누르는 "같은 요청으로 확인"(같은 키·같은 본문)              |
| 409 `session_conflict`, 409 `turn_indeterminate`   | 영구 종료                 | 각각의 종료 안내                   | 새 검색(새 키)만                                                             |
| 410 `session_expired`                              | 영구 종료                 | 확인 시간이 지났다는 안내          | 새 검색(새 키)만                                                             |
| 501 `confirm_unsupported`                          | 영구 종료                 | 기준 확인을 지원하지 않는다는 안내 | 새 검색 버튼도 두지 않는다                                                   |
| `confirmation_required`                            | 확인 대기                 | 기준 확인 질문과 답변 입력         | 답 제출(`POST /v1/search/confirm`). 원 질문에 답을 붙여 새로 검색하지 않는다 |

- "계약 밖 본문은 불명"은 5xx에만 해당한다. "계약과 다른 응답은 종료"는 2xx 본문을 검증하는 단계의 이야기이며 둘을 같은 상태로 보지 않는다.
- 501 `confirm_unsupported` 등 서버가 처리하지 않았다고 밝힌 종료 사유는 일반 5xx보다 먼저 가른다. 500이라는 숫자나 문구로 확정 실패를 추측하지 않고, 모르는 오류 code를 처리 중으로 추측하지도 않는다.
- SSE `error` 이벤트에는 상태 코드가 없어 code로 옮긴다. `turn_in_progress`·`session_conflict`·`turn_indeterminate`는 409 의미로, `timeout`은 504로, 그 밖은 500으로 본다.

### 처리 중

- HTTP 응답은 `Retry-After`만큼 기다린 뒤 버튼을 연다. 이미 열린 SSE의 `error` 이벤트는 헤더가 없어 고정 2초 동안 버튼을 잠근다.
- 자동으로 다시 보내지 않는다. 사용자가 누르면 같은 키·같은 본문을 보낸다.
- 질문을 바꾸면 이전 요청의 늦은 409와 대기 타이머는 새 화면을 바꾸지 못한다.

### 처리 결과 불명

- 서버가 요청을 받았는지, 저장했는지 알 수 없다. 실패로 단정하지 않고 성공도 약속하지 않는다.

### 확정된 오류 결과

- 계약 검증을 통과한 `outcome: "error"` 응답이다. 같은 요청을 다시 보내는 길은 없다.
- 공개 응답의 오류 결과는 서버가 DB에 저장을 마쳤다는 뜻이 아니다.

### 영구 종료

- 입력창과 "같은 요청으로 확인"은 사라지고 안내와 새 검색만 남는다.
- 세션 secret과 사용자의 답은 React 상태에만 있고 URL·콘솔·브라우저 저장소에 남기지 않는다. 새로고침하면 확인은 처음부터 다시 시작한다.
