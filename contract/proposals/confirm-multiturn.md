# 제안: 기준 확인 멀티턴 (미합의 초안)

상태: **정본 1.5.0으로 대체됨**. 이 문서는 초안 기록이다. 확정된 필드·오류·SSE 순서는 `public-api-v1.openapi.yaml`(1.5.0)을 따르며,
최초 검색 응답이 곧 확인 대기라서 아래 초안의 별도 확인 시작 호출은 쓰지 않는다. mock은 `src/lib/mockConfirm.ts`다.
내부 `query-intent-0.1`은 공개 계약으로 쓰지 않는다. 아래 필드는 화면에 보여 줄 값만 따로 정의한 것이다.

## 흐름

1. 사용자가 "안전한 국내 ETF 5개 보여줘"를 검색한다.
2. 서버가 기준이 모호하다고 판단하면 상품 조회·요약 생성 없이 **확인 질문**을 돌려준다.
3. 사용자가 답을 적거나 "질문 다시 쓰기"를 고른다.
4. 답을 보내면 서버가 **저장해 둔 원 질문의 조건을 유지한 채** 검색을 이어 간다. 웹은 답을 원 질문 문자열에 붙여 새로 검색하지 않는다.

기존 `outcome: ambiguous` + `clarify`는 세션이 없는 "구체화한 새 질문 고르기"이며 이 제안과 별개로 유지한다.

## 1. 확인 질문 응답 `ConfirmationRequired`

| 필드                      | 설명                                                                                        |
| ------------------------- | ------------------------------------------------------------------------------------------- |
| `original_question`       | 사용자가 보낸 원 질문. 화면에 그대로 표시한다.                                              |
| `understood_conditions[]` | 이미 읽은 조건의 표시용 문구(예: `국내 ETF`, `5개`). 웹은 가공하지 않는다.                  |
| `pending_criterion`       | `{ id, label }`. 확정되지 않은 기준 하나. 한 번의 확인에는 기준 하나만 둔다.                |
| `prompt`                  | 확인 질문 문장(예: "안전하다는 기준은 어떤 뜻인가요?").                                     |
| `actions[]`               | 허용 동작: 첫 버전은 `answer_text` 하나다. 질문 다시 쓰기는 새 검색이라 서버 동작이 아니다. |
| `answer_max_length`       | 답변 글자 수 상한.                                                                          |
| `session`                 | 아래 2절.                                                                                   |

"기본 기준으로 계속"(`use_default`)은 어떤 기준을 기본으로 쓸지 합의되지 않아 첫 버전에서 뺐다(열린 질문 2번).
웹이 수치 기준이나 추천 문구를 만들어 넣지 않는다.

## 2. 세션 식별·버전·만료

`session = { id, secret, version, expires_at }`

- `id`: 불투명한 고엔트로피 값. 순번·시각을 담지 않는다.
- `secret`: 최초 응답 본문으로만 전달한다. URL·쿼리에 싣지 않는다.
- `version`: 확인 대기 상태가 바뀔 때마다 증가한다. 제출 때 되돌려 받아 충돌을 감지한다.
- `expires_at`: 절대 시각(ISO 8601). 짧게(예: 10분) 두고, 한 번 이어받으면 소비된다.

## 3. 답변 제출

`POST /v1/search/confirm` (가칭)

- 헤더: `Idempotency-Key`(클라이언트가 시도마다 만든 UUID), `X-Session-Secret`(2절의 `secret`).
- 본문: `{ session_id, version, action, answer? }`. `answer`는 `action = answer_text`일 때만 있다.
- 성공: 완성된 검색 응답(`SearchResponse`)을 JSON 하나로 돌려준다(권고 (a)). 재개 스트림(b)은 열린 질문이다.
- **중복 제출**: 같은 `Idempotency-Key`로 다시 오면 처음 결과를 그대로 재생한다. 다른 키로 같은 `version`을 다시 보내면 충돌이다.
- 응답 `question`은 원 질문이어야 한다(답변 문자열이 합쳐진 질문이 아니다).

## 4. 오류

기존 `ErrorBody` 모양을 재사용한다.

| 상황                                | 상태         | `code`                | 웹 처리                                                                                                       |
| ----------------------------------- | ------------ | --------------------- | ------------------------------------------------------------------------------------------------------------- |
| 만료                                | 410          | `session_expired`     | 처음부터 다시 확인하거나 질문 다시 쓰기                                                                       |
| 충돌(version 불일치·다른 키 재제출) | 409          | `session_conflict`    | 처음부터 다시 확인                                                                                            |
| 서버가 이 기능을 지원하지 않음      | 404 또는 501 | `confirm_unsupported` | 확인 없이 기존 검색으로 진행하도록 안내                                                                       |
| 전송 실패(연결 끊김·시간 초과·5xx)  | —            | —                     | **서버가 처리했는지 알 수 없다.** 자동 재시도 없이, 사용자가 "다시 보내기"를 누르면 **같은 키**로 재전송한다. |

## 5. SSE와 확인 대기

- `POST /v1/search/stream`이 확인이 필요하다고 판단하면 `start`, `interpretation`(읽은 조건)까지 보낸 뒤 `confirmation_required` 이벤트(본문은 1절)를 보내고 **`done` 없이 정상 종료**한다.
- 이 종료는 끊김(`StreamCutError`)과 구분돼야 하므로 이벤트 순서 규칙에 "확인 대기 종료"를 명시해야 한다. 이때 `results`·`answer_*` 이벤트는 오지 않는다.
- 답변 이후 검색 재개는 3절의 JSON 응답으로 받는다.

## 6. 인증 없는 서비스에서 세션 보호

- 세션 id 추측을 막기 위해 128비트 이상의 무작위 값을 쓰고, 제출에는 `secret`을 함께 요구한다.
- 만료를 짧게 두고 성공 제출 뒤 세션을 소비한다. 요청 수 제한은 기존 `/v1/search`와 같은 정책에 포함한다.
- 서버 로그·메트릭에는 `secret`과 답변 원문을 남기지 않는다.
- 웹은 `secret`과 답변을 메모리(React 상태)에만 두고 URL·콘솔·localStorage·sessionStorage에 저장하지 않는다. 새로고침하면 세션을 잃고 처음부터 다시 확인한다.

## 합의가 필요한 열린 질문

1. 성공 응답을 JSON 하나로 할지, 재개 스트림으로 할지.
2. "기본 기준으로 계속"을 허용할지, 허용한다면 기본 기준을 서버가 어떻게 정하고 보여 줄지(합의 후 후속 버전).
3. `confirmation_required`를 스트림 이벤트로 둘지, 일반 검색 응답의 새 outcome으로 둘지.
4. 세션 TTL 값과 요청 수 제한 정책.
5. 한 질문에 확인 기준이 둘 이상일 때 순차 확인을 허용할지(이번 제안은 한 번만).
